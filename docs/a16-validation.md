# A16 增量扫描流水与自然批次提交

2026-09-19，macOS x86_64，本机 Swift 6 Package debug 构建。网络均为 URLProtocol 模拟，保留 DriveClient 的生产限速；没有访问真实 Drive。

## 修复范围

- 将既有文件裁决/传输逻辑抽为同一个调度函数，扫描期间与扫描后的收尾复用，避免两套上传实现漂移。
- 首个变化文件观察立即提交并调度。后续观察按最多 64 条、scanner 批次末尾或目录操作前提交；写事务完成后才按这些 item ID 加载决策输入。
- 候选查询从 `json_each` 中的批次 ID 驱动，通过 CROSS JOIN 固定为主键查找。单纯 `item_id IN (...)` 在本机 SQLite 会选择 dirty 索引、重复扫描整组脏项，故未采用该查询计划。
- 有效基线缓存同时命中文件身份、父项、名称和元数据时，直接跳过逐文件 SQLite 查询；改名继续走原有路径核验，dirty/远端变化项不会进入此缓存快路。
- 最多 6 个并行哈希任务，窗口最多 64 条元数据。小文件沿用内存哈希，大文件使用现有 1MB 流式哈希函数；不再在扫描回调中整块读取大文件。
- 取得传输额度后才创建 Task，传输上限仍为 `max(1, min(64, maxConcurrency))`。没有用无限 Task 等待信号量来凑批。
- 匹配基线/unchanged 等纯数据库回执也按最多 64 条提交。目录就绪或重命名等依赖即时结果的扫描操作使用即时事务，不再等 5ms 凑批计时器；并行传输完成回执继续使用 Group Commit。
- 只有父目录及祖先已确认远端就绪的文件才提前调度；未完成的父目录创建先走既有恢复流程。
- 无传输任务的空跑直接跳过新增的等待阶段，不增加队列切换。
- 上传、下载计数使用锁；已成功的早期任务释放去重记录，失败项在本轮最终收尾时不重复尝试。
- 扫描失败或取消时，等待已启动的传输收尾后再抛错；不进入缺失项检测。最终调度出错时同样先收尾。

## 保留的屏障及原因

1. **完整 Changes 页链仍先于本地传输。** 后续页可能改变同一对象或祖先的范围、删除状态与名称冲突；当前条件写保护能力不能支持把前一页当作最终远端证据。A13 已将 Changes 观察/游标及 inbox 应用改成按页/批事务，审计所述 Changes 逐项 `await batchWrite` 已不适用于当前代码，故不重复改写这条链路。
2. **缺失项检测、文件删除和冲突副本创建仍等待本地扫描成功完成。** 缺失判断需要完整枚举；提前创建冲突副本会使本轮扫描与缺失检测混入新对象。目录删除继续等待文件动作完成及后代屏障检查。
3. 目录映射和 baseline cache 仍从 SQLite 加载；此次消除的是正文传输前的完整本地扫描/哈希屏障，没有宣称启动成本与基线规模无关。初始化上传以及大文件实际传输方式不是本次 A16 的重写范围。

86 项测试通过，覆盖现有根丢失、删除、目录后代保护、持久冲突、失败与发布安全，以及新增 A16 场景：

- 扫描交出首文件后暂停尾目录，真实 multipart 请求已完成；在 HTTP 边界通过独立 SQLite 连接核验观察和 create intent 已提交。
- 尾部正常完成、枚举错误、实际 Task 取消三种结束方式；返回后首文件回执已持久化，未枚举尾目录不会被标记 absent/deleted。
- 1000 条变化元数据但正文匹配的观察：连同回执和整轮固定开销仅 **36 次事务**，计时器触发提交增量 **0**，1000 条摘要与代次全部正确；最后一轮实测 0.325s。
- 80 个新增文件、延迟响应、并发配置 2：全部完成，模拟服务端峰值在途请求为 2，返回后为 0。
- 父目录仅有持久创建意图、远端尚不存在时，先恢复目录创建，再发子文件上传，复用原父目录 ID。
- 批次 ID 查询计划使用 items 主键，而非每批重复扫描 dirty 索引。
