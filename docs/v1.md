# gdrive 重建方案：流式双向同步与小文件高吞吐

版本：1.0  
日期：2026-09-18  
定位：macOS / Swift 库；Google Drive 普通文件与目录双向同步。  
状态：实施设计，未实现、未跑本机或真实 Drive 性能测试。文中数值分为“平台规定”和“初始调优参数／验收目标”，后两者不是实测结果。

## 1. 最终决策

采用“增量索引 + 文件级决策 + 父目录依赖 + 有界流水线”，不采用“完整扫描 → 完整比对 → 完整计划 → 开始传输”。

**新建远端根目录是专用快路径：本地发现文件后，只等待该文件自己的远端父目录就绪、输入稳定、操作意图持久化，即可开始上传。其他文件是否已扫描、其他目录是否已创建，均不是前置条件。**

“最高效率”的具体含义是：在相同一致性与恢复语义下，减少不必要的请求、正文读取、持久化次数和全局等待，并用基准选择参数。不能在未实测时声称一个固定并发值对所有机器、网络和 Drive 项目都是最快的。

### 1.1 产品范围

只做一个同步语义：两端传播普通文件、空目录的新增、内容修改、删除、重命名和移动；内容冲突保留版本；操作中断可恢复；外部修改停止后，在权限、网络正常且无待解决结构冲突时最终收敛。

以一个本地目录和一个远端目录组成一个同步对。第一版一个同步对只由一个本地引擎实例写入；允许用户在 Drive 网页或其他客户端修改远端，但不把多个独立 gdrive 实例协调同一根目录作为已支持能力。

保留 Swift Package 库形态，支持 macOS 14+、Intel 与 Apple Silicon。源代码、测试、测试辅助进程均为 Swift；允许调用系统 POSIX、CryptoKit、Foundation 和 SQLite 接口。本地文件扫描使用 `DirectoryScanner` 库（`/Users/chemzqm/lib/scanner`），该库为 Swift 6 原生实现，基于 Darwin POSIX 系统调用（`openat/fdopendir/readdir/fstatat`），提供固定 OS 线程池、有界背压批次流式接口和目录级剪枝，实测 430K 文件性能与 `rg --files` 相当。不依赖 rclone、Shell 或 Python 完成同步。

不做 Backup、Mirror、方向覆盖模式、旧 schema 迁移、私有打包存储、跨文件事务、Finder 扩展、占位文件或按需下载。Google Docs/Sheets/Slides、快捷方式、符号链接、硬链接关系、ACL、资源叉和扩展属性不在第一版同步承诺内；遇到不支持项必须报告，不能默默当作不存在。普通包目录按目录树处理，不保证正在运行的数据库或应用包具有应用级事务一致性。

文件名称过滤和目录剪枝必须支持；规则以同步对为单位生效。被排除的对象属于 unmanaged，不属于 deleted。改变过滤规则必须重新建立受影响区域的管理状态，不能触发意外删除。

### 1.2 保证边界

承诺的是文件级可恢复发布、已捕获内容不被静默丢弃、可信证据驱动的删除、最终一致；不是任意外部写入者之间的全目录线性一致事务。

目录总数、总字节数、完整计划、精确百分比都不得成为执行前置条件。一次运行可以已经上传部分文件，又在另一个目录报告读取错误；错误阻断对应范围和完成声明，不回滚无关成功传输。

## 2. 五个内部职责

| 职责 | 内容 | 禁止承担的工作 |
|---|---|---|
| SyncEngine | 驱动事件循环、依赖调度、资源预算、恢复与状态输出 | 不执行阻塞读盘，不把整棵树变成任务数组 |
| Reconciler | 对共同基线 B、本地 L、远端 R 作文件／目录级决定 | 不调用网络，不自行扫描目录 |
| StateStore | SQLite 中的身份映射、观察状态、基线、意图、游标和扫描完整性 | 不保存另一套重复 JSON 状态，不在事务内等网络 |
| LocalFiles | DirectoryScanner 集成、事件提示、稳定读取、下载发布、本地恢复 | 不自行选择远端覆盖方向 |
| DriveClient | 身份认证接口、REST、传输、分页、响应解析、错误分类 | 不隐藏自动覆盖，不把所有失败统一重试 |

这是五个职责，不要求五个 package，也不建立通用插件框架。账号、token 刷新与必要的沙盒授权由宿主提供；同步核心不依赖有签名的测试 App 才能运行离线测试。

### 2.1 宿主调用契约

对外只暴露打开同步对、执行／唤醒同步、观察状态、取消四类能力；名称可随代码风格确定，不要求用户先得到完整 plan。凭据提供者负责 token 获取与刷新，过滤规则和资源预算属于打开同步对时的配置。

同一同步对多次唤醒合并到同一个协调循环，不并行启动两个完整运行。网络回调带 operationID 与 generation；旧回调不能覆盖新状态。取消停止产生新副作用，保存未知结果与已完成结果；再次运行先恢复，不丢弃状态从头重建。

状态流提供发现数量、队列数量、已完成数量、已知字节、冲突和当前等待原因。发现尚未结束时，总文件数与总字节数明确为未知，不给出伪精确百分比。状态观察不触发全树扫描。

## 3. 远端根目录：必须区分“新建”与“丢失”

### 3.1 根绑定输入

对外只提供两种绑定意图，不是两种同步模式：

- `existing(rootID)`：连接确切的已有 Drive 目录。
- `create(parentID, name)`：在已知父目录下创建一个新的同步根，并永久记录返回的 ID。

宿主已有确切 ID 时，不再按名称查找。按路径定位属于绑定阶段：只查必要的父链和目标名称，不扫描整棵 Drive。

同名目录允许存在于 Drive。需要自动选择已有目录时，必须检查全部匹配结果；匹配多个即报告歧义，不能任取第一个。[S4][S10]

### 3.2 三种证据状态

| 状态 | 如何得到 | 能做什么 |
|---|---|---|
| FreshCreated | 本次持久化创建意图对应的目录创建成功，身份已确认 | 未映射的新文件可走无需远端全树比对的 create 路径 |
| ExistingKnown | 用户绑定确切 ID，或从可信基线恢复 | 按映射与增量／目录级证据执行 |
| UnknownOrLost | 原来绑定的根不可访问、返回 404、权限不明、类型改变 | 暂停该同步对，保留本地数据与状态 |

Drive 的 404 同时可能表示不存在或无读取权限。因此，不能把“旧 rootID 返回 404”转化为“创建新根并重新上传”，更不能推断本地应被清空。[S11]

FreshCreated 证明该目录在创建时没有历史子项，不证明它永远没有其他写入者。后续外部新增、移动或同名对象仍通过 Changes 与结构检查处理，保留冲突。它不是远端互斥锁。

### 3.3 初次启动的并行准备

以下工作尽可能并行：

1. 获取同步对范围内排他写入锁，检查同步对与本地根身份；重叠本地／远端根拒绝并行写入。
2. 本地开始扫描，并记录本地事件观察起点。
3. 获取并持久化远端 Changes 起始 token `C0`。
4. 异步补充预生成 ID 池。
5. 仅执行必要的绑定、父目录可写性与完整可见性检查。

必须在第一项远端写入前取得 `C0` 并持久化，防止遗漏初始化过程中的外部变化。这里是一项固定开销，不是消费全部历史 Changes，更不是远端全盘扫描。当前 API 的 Changes token 是 opaque token；不按字符串或数字比较其大小。[S7][S8]

任意外部客户端添加的文件也在同步范围内时，凭据必须具备完整的目标树可见性和写入能力。第一版要求宿主提供适当的 `drive` scope；不能将 `drive.file` 的 app 可见集合当作完整目录。[S12]

## 4. 核心快路径：边发现、边建树、边上传

### 4.1 单文件就绪条件

对文件 f 定义：

```text
ReadyToUpload(f) =
    AuthReady
    AND RemoteParentConfirmed(f)
    AND StableInputPrepared(f)
    AND DurableIntentCommitted(f)
    AND ByteBudgetGranted(f)
    AND RequestBudgetGranted(f)
```

公式中没有 `EntireLocalScanComplete`、`EntireRemoteScanComplete`、`AllHashesReady`、`AllDirectoriesCreated` 或 `PlanApproved`。

同一父目录创建只允许一个未完成操作。其他任务按 parent item ID 等待共享的目录就绪事件，不重复发送创建请求，也不占据传输 worker 睡眠等待。

### 4.2 流水执行

```text
本地条目流 ──→ 基于身份与证据的逐项决策 ──→ 持久化待执行意图
                    │                         │
                    ├── 目录依赖队列 ────────┤
                    │   父目录成功即释放子项   │
                    └── 文件输入准备 ────────┤
                                              ↓
                                      已就绪文件传输队列
                                              ↓
                                       响应校验与逐项提交
```

扫描、建目录、准备文件、上传、处理 Changes 和提交已完成项交错运行。它们共享预算，不是六个串行大阶段。

示例：

```text
local/
  a.txt
  src/
    b.swift
    very-large-tree/...
  assets/
    c.json
```

允许的执行顺序：

```text
扫描发现 a.txt                         准备 a.txt 的字节和摘要
新远端根创建成功                       立即上传 a.txt
发现 src/、assets/                     并发创建两个目录
src/ 创建成功                         上传 b.swift
assets/ 创建成功                      上传 c.json
very-large-tree 仍在扫描                上述文件已完成传输
```

不能先递归创建所有目录，再处理任何文件。

### 4.3 目录依赖与调度

目录只有在父目录已经被确认创建后，才允许创建自身。即使已经提前分配所有 ID，也不能假定服务器会接受指向尚未创建父目录的文件。

Drive batch 不保证内部请求执行顺序，不能将相互依赖的父目录和子目录创建放进同一 batch。独立兄弟目录才可合批；首文件祖先链优先使用立即发送的请求，不等凑满批次。[S2]

调度采用有限就绪窗口。优先级为：解除阻塞的目录请求／恢复未知结果 → 已就绪小文件 → 普通传输与索引工作；使用等待年龄提升避免大文件和较深目录饿死。已有就绪文件持续运行，目录请求不得把全部网络预算占满。

远端根不存在但所有文件都位于很深的父链下时，父目录创建的串行网络往返是真实依赖。不得承诺与目录深度无关的首次上传延迟，也不应为了隐藏这一延迟，把文件先上传到临时远端根，再为每个文件增加一次移动请求。

### 4.4 适用于新子树

已有同步根内发现新的本地目录，且其远端对应位置缺失已经得到可信的父目录级证据后，创建该远端目录。其首次建立的子树同样走 FreshCreated 路径，不再对子树中每个文件执行名称查询。

只跳过不存在历史状态的比对，不跳过身份持久化、输入稳定性、结果确认和外部变化处理。

## 5. 预生成 ID：摊薄开销并使重试幂等

用 `files.generateIds` 批量获取 ID。Google Drive API 单次调用最大上限为 1000 个（实测耗时约 1.5 秒）。生产配置直接采用单次 1000 个，低水位 200 个。补充请求与本地扫描、传输并发进行，严禁每个文件单独请求 ID。[S5]

目录和普通文件新建全部使用预生成 ID。在发起远端创建请求之前，本地从内存 ID 池中为新发现项分配好服务器认可的永久 ID，并随操作意图持久化到 SQLite（`operations.target_remote_id` 与 `items.remote_file_id`）。整棵目录树在本地的父子 ID 引用拓扑是瞬时就绪的，完全无需等待远端网络响应来获取或回传 ID；尚未使用的池内 ID 可以安全丢弃，不影响已有文件身份。

Drive 官方说明，预生成 ID 创建成功后再次尝试会返回 409，从而避免重复对象；文件夹同样支持预生成 ID。[S1]

409 不是自动成功。查询同一 ID，检查账号、父目录、对象类型、操作标记、文件大小与内容摘要。对成功但响应丢失的操作，先确认既有对象；禁止换 ID 重传。对于大于 8MB 的文件分块续传（Resumable Upload），会话中断后亦严格沿用同一预分配 ID 进行核验与断点恢复，杜绝换 ID 造成的孤儿文件。

小文件的正常创建直接发送带 ID、parent、name 与内容的 multipart 请求，不先创建一个空文件再更新正文。

## 6. 本地扫描：DirectoryScanner 集成与哈希流水线

### 6.1 扫描接口

使用 `DirectoryScanner` 库（`/Users/chemzqm/lib/scanner`）的批次流式接口 `scanner.scan(request)` 执行本地文件树枚举。该库基于 Darwin 原生系统调用（`openat/fdopendir/readdir/fstatat`），内部维护固定 OS 工作线程池与有界背压通道，不占用 Swift cooperative executor。

扫描配置：

```swift
let options = ScanOptions(
    mode: .basic,              // 获取 FileMetadata：identity(dev+inode)、mtime、ctime、size
    emission: .all,            // 同时输出目录和文件，目录条目用于依赖图构建
    includeHidden: true,       // 由同步对过滤规则决定
    workers: min(8, cpuCount), // scanner 内部管理线程池
    delimiter: 0x00            // NUL 分隔，便于零拷贝路径传递
)
```

同步对的过滤规则转换为 `FilterRule` 数组传入 `ScanRequest`。命中 `.excludeDirectory` 的目录在 `openat` 前剪枝，跳过整个子树。被排除的对象属于 unmanaged，不属于 deleted。

扫描器不负责计算哈希，也不等待某个文件读完再列举下一个目录。列举名称与读取内容严格分开。

### 6.2 扫描与哈希流水线

scanner 输出的 `ScanBatch` 通过有界队列传递给独立的 SHA-256 计算线程池，形成两级流水线：

```text
DirectoryScanner.scan()
    │  固定 OS 线程池，openat/readdir/fstatat
    │  有界 BatchChannel（容量 workers×2），满载时生产者等待
    ↓
ScanBatch 消费 → 逐项分流
    │
    ├── 目录条目 → 目录依赖图构建 + 远端创建调度
    │
    └── 文件条目 → 快速变更检测（identity + mtime + size 与数据库缓存比对）
            │
            ├── 全部匹配 → 跳过（不读内容、不算 SHA-256）
            │
            └── 不匹配或无缓存 → ComputeQueue（有界背压队列）
                    │
                    └── SHA-256 工作线程池（独立 OS 线程，初值 max(1, cpuCount)）
                            │
                            └── 逐项决策 + 持久化意图 + 传输队列
```

快速变更检测利用 scanner `.basic` 模式一次 `fstatat` 获取的 `FileMetadata`：`FileIdentity(device, inode)` 确认文件身份未被替换，`modificationTime` + `fileSize` 与数据库缓存的上次同步值比对。三项全部匹配时，该文件以极高概率未被修改，跳过内容读取与 SHA-256 计算。证据不可信时（如 ctime 变化但 mtime 未变、曾观察到 identity 回收等）回退到重新计算摘要，不能将 mtime+size 当作绝对内容证明。

SHA-256 计算队列参考 scanner 的 `sha256-test` 示例，使用 pthread mutex + cond 实现有界背压。计算线程直接以 POSIX `open/read` 操作文件，每线程维护独立的读缓冲区和 SHA-256 上下文，不跨线程共享可变状态。

任何队列同时受条目数量与字节数量约束。生产者在满载时等待，不丢弃条目，不无限堆积任务。

### 6.3 scanner 提供的保证与限制

scanner 已满足以下设计要求，不需要 gdrive 重复实现：

- **有界背压**：`BatchChannel` 容量 `workers×2`，满载时工作线程挂起于 `pthread_cond_wait`，消费者跟不上时自动背压。
- **过滤与剪枝**：`FilterPlan` 预编译规则，ASCII 路径走 `memcmp` 快路径。
- **不逐项创建 URL/Foundation 对象**：全程 C 指针操作。
- **公平调度**：子目录入队失败时转本地 DFS，不会所有 worker 被一个大目录独占。
- **安全取消**：消费者抛错时 `scheduler.stop()` + `channel.fail()` 广播终止，所有目录句柄安全关闭。
- **根身份**：`ScanSummary.rootIdentity` 提供根目录的 `(dev, inode)`，可用于验证同步根未被替换或卸载。

scanner 不提供的，由 gdrive 补充：

- SHA-256 计算（独立线程池）。
- 内容稳定性检测（捕获前后 fstat 比对）。
- 增量扫描与 FSEvents 集成。
- 目录完整性证据记录。

`AsyncStream` 的丢弃旧值／新值策略不适合保存同步工作。可以对 UI 进度合并最新状态，但不得对文件发现、操作结果或 Changes 事实丢消息。

### 6.4 性能门槛

扫描性能由 DirectoryScanner 库保证：实测 430K 文件中位耗时与 `rg --files` 相差约 3%，用户态 CPU 开销降低 50% 以上，满足 `T_swift / T_rg ≤ 1.10` 的门槛。gdrive 不重复验证扫描本身的性能。

gdrive 额外度量：

- 扫描到首文件决策的调度延迟（从 `ScanBatch` 交付到逐项决策完成）。
- SHA-256 计算吞吐（files/s、MB/s），至少比较计算线程 1/2/4/8 的效果。
- 快速变更检测命中率：未变化场景中跳过 SHA-256 的文件比例应 > 95%。
- 端到端扫描+哈希管线吞吐，不能拿单独的扫描速度代表完整本地工作性能。

## 7. 输入准备与摘要：小文件不落临时正文

### 7.1 小文件路径

初始分界设为 4 MiB，低于官方 multipart 适用范围 5 MB。对于稳定的小文件：[S1]

```text
获得内存配额
→ 打开文件并 fstat
→ 一次读取到不可变 Data，并计算 SHA-256
→ 再次 fstat／核对路径身份
→ 持久化 {generation, targetID, size, SHA-256, operationID}
→ 从同一份已捕获字节构造 multipart 并发送
→ 比较服务端结果
→ 提交对应 generation
```

不做“扫描时读一遍算 hash → 封存复制一遍 → 上传再读原文件一遍”。小文件正常路径不生成一份磁盘 spool。multipart 拼接与 Foundation 可能产生的缓冲复制都计入字节预算，不能把 Data 写时复制称作端到端零拷贝。

新根上传没有历史正文需要比较，首次摘要只是对当前捕获内容的记录与传输验证。只要求当前文件准备好，不要求整个目录全部算完 SHA-256。

捕获期间文件变化则丢弃这次不稳定读取，有限重试并合并到最新 generation，不能把截断或拼接的数据当成稳定版本。长期持续写入的文件标记 waitingForStableInput，其他文件继续。

### 7.2 上传期间又修改

上传的是已捕获 generation g。上传期间本地变成 g+1，成功响应只允许确认 g 的已发布内容；必须保留 g+1 为 dirty，不能把当前路径整体标成同步完成。

客户端崩溃后，先恢复目标 ID 和操作结果。远端已成功则确认旧 generation；未成功且本地仍匹配记录摘要时重捕获重试。源已改变时重新决策，不把新内容混入旧请求，不要求永远保存所有从未完成同步的瞬时版本。

### 7.3 大文件路径

大文件使用稳定的磁盘 staging 输入及 resumable upload。支持同卷文件克隆时优先验证并采用克隆，其他情况流式复制和计算摘要，不能在每次重试时重新读取会变化的原文件。

一次只准备有限数量的大文件；staging 有磁盘配额，额度不足只阻塞相关大文件，不能挤占小文件内存和所有传输槽位。

resumable 正文优先减少请求数，网络适合时连续发送整个剩余内容；需要分段时使用较大、按 256 KiB 对齐的块，而不是默认所有文件都切成最小块。会话 URI 与已确认偏移持久化，恢复以服务端确认的偏移为准，不以客户端已发送字节数为准。[S1]

### 7.4 摘要策略

统一的内容标识用 SHA-256，不默认同时计算 MD5 和 SHA-256。普通未变化项优先利用 scanner `.basic` 模式提供的 `FileMetadata`（`FileIdentity(device, inode)` + `modificationTime` + `fileSize`）与数据库缓存的上次同步值比对；三项全部匹配时跳过内容读取与 SHA-256 计算（见 §6.2 快速变更检测）。证据不可信时（如 `changeTime` 变化但 `modificationTime` 未变、曾观察到 identity 回收等）回退到重新扫描／摘要验证，不能将 mtime+size 当作绝对内容证明。

Drive 的 `sha256Checksum` 是“如可用则返回”，不是对每个对象无条件存在；普通文件之外的 Docs 和 shortcut 不适用。[S4]

上传创建／更新的响应尽量一次索取：

```text
id,name,mimeType,parents,size,sha256Checksum,version,trashed,appProperties
```

摘要与大小齐全且匹配，正常路径不再追加 `files.get`。摘要暂缺的项进入待验证队列，有限延迟补查；持续缺失时，以按需读回计算摘要作为异常验证路径，或报告无法核验。不得将“缺字段”当作校验通过；不得因此阻塞无关上传。

## 8. 网络调度：共享会话、有限并发、元数据不能挨饿

### 8.1 初始资源预算

以下只是第一轮 benchmark 的统一起点：

| 参数 | 初值 | 必须维持的性质 |
|---|---:|---|
| scanner workers | min(8, cpuCount) | 由 `ScanOptions.workers` 配置，scanner 库内部管理线程池 |
| SHA-256 计算线程 | max(1, cpuCount) | 独立 OS 线程池，通过 ComputeQueue 有界背压连接 scanner 输出 |
| 输入准备 worker | 2 | 负责大文件 staging 与稳定性检测，与扫描、网络 worker 分开 |
| 文件传输并发 | 16 | 在 4—32 内按实测反馈调整；先覆盖 4／8／16／32 |
| 大文件传输上限 | 2 | 不独占全部传输容量；总预算之内 |
| 元数据逻辑并发 | 4 | 至少 1 个可用额度留给目录解锁／恢复／Changes |
| 已发现条目内存窗口 | 4096 项 | 超额背压；已有持久工作按页加载 |
| 已准备正文与请求缓冲预算 | 64 MiB | 包含在途正文、multipart 缓冲和下载缓冲 |
| 普通批次持久化 | 最多 64 项或约 5 ms | 首文件／祖先目录意图立即提交，不等凑批 |
| UI 进度输出 | 最多约 4 次/秒 | 合并进度，不合并丢失最终结果 |

网络请求额度与字节额度分开：先获得字节配额才读取正文；只有依赖都就绪后才获取实际网络槽位。不能让全部上传 worker 在等待父目录时占满槽位，也不能先读几万个文件再等网络。

### 8.2 URLSession 与观测

使用一个长期复用的 URLSession 管理普通 metadata 和 media 请求，保持统一认证与连接使用策略，不为每个文件新建 session。记录 URLSessionTaskMetrics，用实测协议、连接复用、排队和网络耗时判断瓶颈；不能仅设置一个 HTTP 连接数就断言有多少 HTTP/2 并行流。[S15][S16]

元数据缓存与持久索引不能用 URLCache 的陈旧响应冒充最新远端状态。对一致性关键查询采用明确的缓存策略；认证刷新应 single-flight，不能多个并发文件同时刷新 token。

### 8.3 速率与并发调整

统计最近窗口的已完成文件数、传输耗时、服务端限流、错误率、队列等待、内存占用。队列充足且无错误时逐步增加并发；出现 429 或配额类 403 时降低并发并延迟后续请求。不能把所有 403 都当限流，权限拒绝不是可通过增加等待自动修复的错误。[S3][S11]

截至本方案日期，官方配额页已以 quota units 描述限制，不能再硬编码旧的“每分钟固定若干个请求”模型。限速器按方法成本、项目／账号实际配置和服务端反馈工作；batch 内部子请求仍分别计算，外层 HTTP 数与逻辑请求数都要记录。[S2][S3]

重试使用抖动和单调时钟截止时间；取消、退避与网络超时都必须受同一剩余预算约束。未知写入结果走状态确认，不能套普通读取请求的自动重试。

### 8.4 Batch 的正确位置

batch 只用于已经独立就绪的 metadata 请求，每批不超过 100 个；不上传、下载或导出媒体内容，不串联父子依赖。[S2]

启动阶段和解除阻塞的关键目录请求立即发送。稳态积累足够独立任务时再考虑合批；高 RTT 不等于所有情形都需要最大 batch，必须比较其 p95 延迟和总吞吐。

不强制 gzip 文件正文，不私自压缩后作为不同内容保存。元数据响应可以利用受支持的压缩，不改变用户的普通远端文件结构。

## 9. 已有根：文件级与目录级证据，不退回全局计划

### 9.1 三方状态

对每个同步项保存共同基线 B、本地观察 L 和远端观察 R，内容与位置分开比较。mtime 不决定谁覆盖谁。

| 相对 B 的变化 | 决策 |
|---|---|
| 只有 L 内容变，R 未变 | 条件上传对应内容 |
| 只有 R 内容变，L 未变 | 下载并安全发布 |
| L、R 内容都变且摘要相同 | 不传正文，更新共同基线 |
| L、R 内容都变且摘要不同 | 保留双方版本，形成确定的冲突项 |
| L 删除、R 未变 | 满足删除证据后传播到远端回收站 |
| R 删除、L 未变 | 满足删除证据后执行本地可恢复移除 |
| 一侧删除、另一侧修改 | 保留修改版本，记录删除冲突 |
| 同一项一侧移动、另一侧改内容 | 无结构冲突时合并位置与内容维度 |
| 双方移动到不同位置／目标被占用／类型冲突 | 阻塞对应项或最小子树，保留内容 |
| 无 B，一侧有内容 | 只能在对应命名空间缺失已获证实后新增 |
| 任一侧 Unknown／Excluded | 不推断删除，不标记同步完成 |

### 9.2 已有映射

已知 fileId 的项，不需要扫描全部远端目录才能得到它的当前身份。Changes、已验证的本轮 metadata 或必要的单项查询更新 R，逐项触发决策。已经具备有效证据的任务可以直接运行；必要的远端并发前置条件不能省略。

### 9.3 无映射但远端父目录已存在

对尚未确认身份的名称，必须取得足以排除同名、同规范化名称和类型歧义的父目录级证据。可对少量启动关键项使用选择性查询；稳态大量文件采用父目录分批列举，避免每文件一次 get/list。

一个目录的分页结束只证明其直接子项枚举完成，不要求所有孙子目录也完成。某个子目录一旦具备完整证据，其工作立即执行，不等其他子树。

Google Drive 的 list 可能返回少于 pageSize 的结果；是否结束以 nextPageToken 是否存在为准。`incompleteSearch=true`、分页中断或 token 被拒绝，都不能把未看到的项判成不存在。[S10]

### 9.4 增量索引与 Changes

首次已有根初始化：先记录 C0，再按目录流式建索引，同时消费 C0 之后的变化。旧扫描结果不得覆盖已知更新的远端版本；对同一 fileId 以观察的版本与扫描 generation 去重。目录完整性独立记录，不以某一页成功代表全目录成功。

每页 Changes 的远端观察更新、dirty 标记和下一页 token 在同一事务中持久化。文件传输是否完成不影响接收下一页；共同基线只在对应操作确认后推进。读取一页不加载整棵 SQLite 树。[S7][S8]

Changes 是用户／shared drive 范围，不是天然按某个目录递归过滤；本方案在本地维护 parentID 图并筛选目标子树。根外无关事件不引发同步根重扫。同页共享祖先解析结果；祖先链不明时先标为待解析，不猜归属。

目录从根外移入时，要为该目录建立子树索引，不能假定所有后代都会各产生一个可供使用的 Change。目录在根内移动时更新父边和名称，不重传整棵目录正文。

已知自己的写入仍可能夹杂外部修改。只有精确匹配 operationID、fileId、version 与内容结果的自事件才能消除重复工作，不能按“这是本 App 写的”过滤整个对象的后续事件。

### 9.5 连续运行与断线重连

是否让库持续运行由宿主决定，不要求另起常驻服务。宿主常驻时，本地事件按受影响目录合并，建议稳定窗口初值 200 ms、最长等待 1 秒；第一次同步没有这段 debounce。远端没有本地事件也必须定期检查，建议有活动时约 5 秒、空闲时约 30 秒作为调优起点，不声称与 iCloud 有同等服务端推送能力。

本地唤醒或网络恢复可以提前触发远端检查，但避免每个文件事件各请求一次 Changes。第一版不引入公网 webhook 服务。周期是宿主调度参数，不是同步正确性的依据。

网络、权限或设备事件观察中断后，保留未完成意图与游标。恢复时先验证根身份和索引可信性，重放相关变化；不能因“离线太久”直接清除数据库。可信事件历史无法衔接时补扫对应范围，补扫期间仍允许已经具备安全证据的无关操作继续。

### 9.6 删除记录与状态回收

删除记录保留原 item 身份和删除 generation，不只保留旧路径。只有两端删除已确认、相关操作终态且必要的观察进度已越过该操作后，才允许回收 tombstone；不存在多客户端已确认协议时，不宣称可借此安全协调任意其他 gdrive 实例。

临时文件、会话和失败操作按持久引用回收，先确认没有恢复依赖，再清理。已确认的操作历史可保留有限数量的诊断信息，不永久追加全量每字节日志。数据库丢失后，已有远端根进入“无基线重新关联”，默认禁止根据单侧缺失传播删除。

## 10. 可靠性：快速 create 与破坏性操作分开证明

### 10.1 持久化状态顺序

统一状态链：

```text
discovered → waitingEvidence / waitingParent / waitingInput
           → ready（意图已持久化）→ inFlight
           → verify / unknownOutcome
           → committed 或 conflict / blocked
```

数据库保存当前项的意图和结果，不保存多套计划文件。`unknownOutcome` 必须先确认旧操作，不创建新操作绕过去。

成功后在同一事务更新：远端身份与确认结果、共同基线的对应 generation、操作终态、需要继续处理的新 generation。用户看到“已完成”的时刻不能早于持久化成功。

### 10.2 SQLite

本地状态目录放在同步根之外，不上传 state、WAL 或 staging。使用 WAL、单 writer、短事务、索引查询、准备语句；读状态可使用独立只读连接。避免长读事务阻止 checkpoint，也不在每个进度回调写数据库。[S13]

意图、ID 绑定、基线与游标采用需要的持久化强度，不用 `synchronous=OFF/NORMAL` 假装已经获得掉电后相同的 durability。建议关键库使用 `synchronous=FULL`，macOS 对需要的同步操作启用并验证 `fullfsync`；以 group commit 摊薄等待，首文件例外即时提交。[S14]

checkpoint 必须受 writer 的串行化控制。官方 2026 年披露了涉及并发写入／checkpoint 的 WAL-reset 问题，固定版本或验证平台修复情况，同时禁止独立后台连接与 writer 同时 checkpoint。这是持久化实施检查，不增加另一套脚本工具。[S13]

### 10.3 最小数据结构

| 表／记录 | 必需内容 |
|---|---|
| roots | account identity、local root identity、remote rootID、绑定代次、过滤版本、引导状态 |
| items | itemID、父 itemID、名称、local identity（对应 scanner `FileIdentity(device, inode)`）、local mtime／size 缓存（用于快速变更检测，见 §6.2）、remote fileId、B/L/R 的内容与位置观察、dirty generation、tombstone |
| operations | opID、itemID、类型、预期 generation／远端前置条件、目标 ID、输入摘要、会话与偏移、状态 |
| directory_observations | 目录的本地／远端扫描 generation、分页状态、完成／Unknown 证据 |
| cursors | 按账号的 Changes token、本地事件观察位置、可信性标记 |

索引至少覆盖 remote fileId、local identity、parentID+nameKey、dirty 状态、operation state 与依赖 parentID。路径由父边按需构造；目录重命名不批量重写所有后代路径。

活跃就绪项只取有限页进入内存，pending item 与 dirty 标记以持久状态为真值，避免一百万个 item 对应一百万个活跃 Swift Task。

### 10.4 远端并发覆盖：必须先过协议验证门槛

Drive `version` 是只读、单调递增的观察值，不等于可在 update 中设置的 compare-and-swap 条件。当前查阅的 v3 update 文档不足以证明每条写入路径都提供需要的原子版本前置条件。[S4][S9]

不能把“上传前 get 一次 version”或“上传后 SHA-256 相同”当作不存在丢更新窗口的证明。后验校验只能检查上传结果，不能证明没有覆盖另一个客户端刚发布的内容。

在第一阶段用 Swift 真实 Drive 契约测试验证可用的条件写语义：metadata rename/move/trash、multipart 覆盖、resumable 初始化与最终发布分别测试。旧条件必须拒绝，故意错误的条件必须拒绝，上传期间另一客户端更新时不能被静默覆盖。保存实际响应 header 和 status 作为测试结果，不能借用 Calendar 或旧 GData 文档作 Drive v3 的能力证明。

验证成立的路径才启用相应自动覆盖；条件失败重新观察并进入冲突决策。无法证实的破坏性路径保留内容并报告 blocked，不能为了“完整自动化”退回无条件覆盖。此项阻断完整可靠双向同步的发布，但不阻断新根 create 流水线和性能开发。

多个独立 gdrive 同时初始化同一远端父目录也不具有名称唯一性事务；第一版禁止这种运行拓扑。单实例锁只解决本机并发，不能声称等同远端分布式锁。

### 10.5 本地下载发布

下载写到目标同卷临时路径，流式计算摘要，校验通过后按文件级发布协议替换。已存在目标需要重新核验本地身份与 generation，保留被替换对象直到发布确认；目标被其他写入者抢占时进入冲突，禁止无条件覆盖。

文件名不存在时采用不覆盖已有项的发布方式。rename 的原子性不等于对任意编辑器的内容 CAS；跨检查窗口发生写入时，保留旧对象与事件证据并重新决策，不能宣称任意外部写入者都被锁住。

大文件下载续传使用 Range，并核验返回状态、范围和目标内容版本／摘要。响应退回完整内容或远端版本改变时，不将新旧片段拼接。完成时校验完整摘要后发布；metadata 已由 Changes 提供且内容匹配时不额外做每文件后验 get。[S17]

## 11. 删除、移动、冲突与最终收敛

### 11.1 删除屏障是局部的

扫描未完成只能说“还没看到”，不能说“已删除”。删除必须同时满足：存在共同基线；缺失侧相应目录／子树已可靠观察；对端没有相对基线的新修改；相关操作已完成／取消；对应破坏性操作的并发保护通过。

在不能排除跨目录移动时，延迟该项删除，等待必要的移动关联窗口或扫描范围完成；不得拖住已确认的新文件上传。目录删除需要后代级证据，不能只检查父目录 metadata version。

Drive Changes 的 `removed` 包括删除与失去访问权限；404、分页错误、权限不足都不是删除证明。[S6][S11]

本地优先可恢复移除，远端只进入回收站，不自动永久删除。同步根本身被删除、卸载或身份替换时暂停整个同步对，不传播为百万文件删除。

### 11.2 远端目录删除的额外边界

远端“先查询目录为空，再把目录放进回收站”不是原子的空目录条件删除；其间外部客户端可能新增子项。目录 version 也不能被假定覆盖所有后代的变化。

因此，目录清理晚于后代同步，保留完整恢复意图，并在并发子项出现时撤销目录清理／恢复目录，报告结构冲突。无法证明安全的范围允许保留待清理空目录并报告，而不是冒险递归处理未知内容。永久删除不属于自动路径。

本地移入／移出同步根、远端移入／移出同步根，都必须结合既有身份与内容变化决定传播行为；不能将权限丢失混为移动，也不能让旧身份 tombstone 删除后来同路径的新对象。

### 11.3 冲突

内容冲突默认保留两个版本。使用稳定的 conflictID（原 item 身份和双方内容标识导出）与持久化目标 fileId，生成稳定的冲突副本名；重试不不断新增副本。

第一次出现冲突时确定原路径保留哪个已存在版本，另一版本用冲突名保存；该决定持久化，两端使用同一决定。用户后续修改冲突副本时，它作为普通同步项继续同步，不能再次自动覆盖。

名字相同但大小写／Unicode 映射无法在本地唯一表示，必须报告名称冲突。Drive 允许同名对象，本地映射不得用一个字典条目静默覆盖另一个远端 ID。[S4]

### 11.4 何时报告“本轮已收敛”

选择一个可说明的本地观察 generation 与远端 Changes checkpoint。只有该范围的观察完整、dirty 项已处理、操作没有未知结果、摘要完成核验且无待解决冲突，才报告本轮收敛。

新变化可以进入下一代继续处理，不要求在持续写入的世界中等待永久静止。已有成功传输不等待最后的收敛报告；所有完整性屏障限制“宣布完成”和相关破坏性操作，不限制无关 create。

## 12. 正常请求与本地工作预算

对于 N 个小文件、D 个新建目录、ID 池批量大小 G（默认采用 API 最大批量 1000）：

```text
正常新建主体请求数 ≈ N + D + ceil((N + D) / 1000) + K
```

例如对于 10,000 个文件，预生成 ID 带来的网络请求仅为 10 次，开销占比降至千分之一。K 单独统计绑定、起始 token、Changes 页和必要的最终检查；Changes 页数可能随变化量增长，不能将 K 宣称为严格常数。重试、摘要缺失、外部冲突也必须分别列出，不隐藏在主体吞吐中。

目标是每个新小文件正常路径一次 multipart media 请求，不附带逐文件存在性 GET、名称 LIST、单项 generateIds、空文件 create、独立 metadata PATCH 或正常后验 GET。

不上传到临时远端目录后再逐项 move，不打包小文件，不用无限并发掩盖过多请求。

正常本地每文件：一次稳定正文捕获及同遍 SHA-256；不变项不读正文；仅所需元数据系统调用；按批意图和完成提交。实际系统调用、正文读取量和临时磁盘量必须被 benchmark 记录。

## 13. 全 Swift 测试与工具组织

建议一个 package，一个库 target，两个 test target（离线与 LiveDrive），共享少量 Swift 测试辅助代码。仅崩溃测试使用一个小型 Swift 子进程；性能和 fixture 生成也由 Swift 完成，不建立第二个 Examples package 或脚本验收系统。

普通入口为 `swift test`；LiveDrive 默认显式跳过，提供测试标签／filter 和受控环境启用。在专用本地临时目录与专用远端测试根运行，凭据由测试宿主提供。默认测试不需要 OAuth、Keychain 或 App 签名。

### 13.1 第一批必须写的流式测试

| 场景 | 必须观察到的结果 |
|---|---|
| 新根 + 扫描器首文件后暂停 | 扫描器未释放时已收到该文件的真实上传请求 |
| 新根 + 最后子树阻塞 30 秒 | 无关文件照常创建／上传，不等 30 秒 |
| src 父目录慢、assets 父目录快 | assets 文件先上传；等待 src 的任务不占传输槽 |
| 父目录创建响应丢失 | 同一 ID 恢复，目录不重复，子项不提前发出 |
| 新建上传成功但响应丢失 | 同一 fileId 被核验，最终仅一个对象 |
| 第一批只有一个文件 | 不等 256 个条目／64 个意图／100 个 batch 子请求 |
| 条目窗口与正文预算耗尽 | 生产者背压，无丢项、无无限 Task、无持续内存增长 |
| 根目录 404 | 不自动重建，不传播本地删除 |

测试不依靠 sleep 猜进度，用可控时钟、屏障和 fake transport 记录实际顺序；真实 Drive 测试再验证 API 行为，不能由 fake 测试替代。

### 13.2 必须覆盖的正确性与故障

覆盖内容双方修改、同大小不同内容、修改时间相同、删除与修改、移动与修改、跨目录交换名字、目录移动入根、同名不同 ID、过滤变化、半页失败、不完整搜索、Events 丢失、Changes 恢复、磁盘不足、取消、源捕获时变化、上传中变化、下载发布时变化、源被删除、会话过期与 Range 异常。

进程终止点覆盖：意图写前／写后、ID 分配后、远端成功后响应丢失、响应成功后状态提交前、本地发布前／后、Changes 行写入与 token 提交边界。用真实 Swift 子进程终止并重启，不用抛异常冒充进程崩溃。

预期树来自测试独立模型，不能调用生产 Reconciler 来生成 expected。最终独立枚举两端、比较命名映射和内容摘要、检查冲突版本保留，并再跑一次验证幂等与无多余传输。

### 13.3 性能数据集

至少包含 1,000／10,000／100,000 文件，0 B／1 KiB／4 KiB／32 KiB／256 KiB／4 MiB 混合，单个大目录、宽目录树、深目录树、混入大文件，以及大量中文和长名称。

测量首次新根上传、首次已有根关联、首次下载、完全不变、小比例内容修改、新增小子树、大目录改名、中断恢复。

对既有根，无变化或少量变化运行的工作量应由相关变化和必要的完整性修复决定，不得每轮退化成全量正文哈希或完整远端扫描。

## 14. 验收指标

### 14.1 首次上传延迟

记录这些独立时间点：syncRequested、firstFileDiscovered、firstInputReady、remoteParentReady、intentDurable、requestBudgetGranted、firstMediaRequestStarted、firstMediaByteSent、firstFileVerified、localDiscoveryCompleted。

定义软件调度附加延迟：

```text
SchedulingDelay = firstMediaRequestStarted
    - max(firstInputReady, remoteParentReady, intentDurable,
          authReady, requestBudgetGranted)
```

健康机器、有工作且无预算阻塞的控制测试，p95 目标不超过 20 ms；如持久化本身慢，其耗时单独记录，不能藏入调度。该值是验收目标，不是实测保证。

新根流式屏障测试必须证明：在扫描器仍被人为阻塞时，首个媒体请求已开始。将数据集从 1,000 扩大到 100,000、且控制首个条目的发现和父链相同时，首文件启动不能因等待总数增长。真实目录布局可能改变发现耗时，必须单独报告。

TTFF 同时报告首个媒体字节发出和首文件确认成功；不能只记录一个任务被放入队列的时间。端到端指标包括认证、网络、根绑定和必要父链开销，不能承诺固定“毫秒内传完”。

### 14.2 稳态吞吐

同机同网络、相同小文件分布、相同上传协议、并发与字段返回条件下，建立“数据已准备、无需扫描比对的直接上传对照”。引擎目标达到该对照有效文件吞吐的至少 90%，同时满足相同内容校验条件，并单独报告为持久化恢复付出的成本。

该对照是本实现的网络路径基准，不是 Google Drive 理论极限。真实云端比较交错运行并报告多轮中位数、p95、错误与重试，不拿一次最快值作承诺。

除 files/s 和 bytes/s 外，必须记录每文件逻辑请求数、外层 HTTP 数、已就绪任务等待时间、有效槽利用率、发现／哈希速率、DB 提交耗时、峰值 RSS、staging 峰值和到收敛的总耗时。

### 14.3 资源与恢复门槛

1 万与 10 万文件场景使用同一窗口和内存预算，正文缓存与活跃 Task 数不得随总文件数线性增长。数据库可随文件数增长，内存缓存有明确上限；实际 RSS 包含系统网络库分配，不能只报自有 Data 总量。

所有故障恢复测试必须证明无静默内容丢失、无同操作重复新建、无错误删除、无基线领先实际结果。未满足该门槛的吞吐提升不计入合格优化。

## 15. 实施顺序与停止条件

### 阶段 A：协议与性能可行性，先做最短闭环

并行实施：集成 `DirectoryScanner` 库、新根创建、批量 ID、边扫描边 multipart 上传、响应字段核验、最小意图持久化；以及远端条件写能力实验。

立即编写"扫描暂停但上传发生"的测试，并跑 DirectoryScanner + SHA-256 流水线与直接网络上传对照。验证快速变更检测（identity+mtime+size）的正确性与跳过率。新根路径不通过流式验收，或扫描到哈希流水线离目标太远时，先修架构，不扩展功能。

本阶段不等待完整双向模型完成才测性能。协议实验不能通过的覆盖／删除路径先明确阻断，不掩盖为已完成。

### 阶段 B：逐项基线与恢复

加入 B/L/R、generation、防重复 ID 恢复、本地发布日志、输入变更处理、下载校验和最小冲突保留。跑进程终止测试，保持阶段 A 性能基准不过度退化。

### 阶段 C：已有根与增量

加入目录级分页证据、Changes 事务游标、FSEvents 提示与丢失补扫、移动关系、过滤与名称冲突。新增无变化／少量变化基准，禁止回归为全树计划。

FSEvents 仅提示需要重查的区域；MustScanSubDirs、UserDropped、KernelDropped 等情况触发相应恢复扫描，不将事件直接当作完整状态。[S19]

### 阶段 D：删除及完整真实 Drive 验收

最后启用已经证实有足够保护的删除／覆盖，覆盖目录级并发、权限丢失、根丢失和掉电持久化检查。真实 Drive 验收只验证专用测试根，不对用户生产目录试错。

完整发布要求：新根低延迟、扫描效率、稳态吞吐、增量复杂度、崩溃恢复与条件写语义均通过。失败项在同一份结果中标明；不制造另一套验收脚本和大量重复文档。

## 16. 实施时不得偏离的约束

- 不将完整 preview/plan 变成执行前置条件，不为精确总进度先扫一遍。
- 不在新建子树逐文件确认远端不存在，不在正常成功后逐文件再 get。
- 不先创建全部目录，不在 batch 中依赖父子顺序，不让等待父目录的文件占满传输 worker。
- 不把源文件多次完整读取包装成“安全检查”，小文件从同一份已捕获正文上传和校验。
- 不用无限 Task／无限 Data 队列追求吞吐，不用关闭 durability 美化性能结果。
- 不将 Unknown、Excluded、404、removed 或未完成分页当作删除。
- 不把单机锁、version 查询或最终摘要核验当作远端原子条件写。
- 不把扫描器较快、模拟测试通过或单次上传成功当作整个同步引擎已经可靠。
- 不恢复 Backup／Mirror 多模式，不引入 Shell／Python 测试编排，不把测试 helper 做成独立产品。
